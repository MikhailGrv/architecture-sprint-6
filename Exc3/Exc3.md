## Проанализируйте текущую архитектуру
1. Основная бизнес-задача - продажа страховок. Критичный сервис core-app
При повышении нагрузки (в первую очередь) необходисол беспечить доступность сервиса core-app

### Что делать
1. Убрать сильную связанность копонентов ИС - переходим на событийную модель. Результат - предсказуемая и распредленная нагрузка внутри ис на core-app:
   1. Добавляем Events-bus (kafka). 
   2. Разворачиваем топики Продукты и Тарифы, Оформленные страховки, Клиенты
   3. Переводим сервисы на отправку/получение данных из Брокера
   4. При этом оставляем интеграцию core-app -> client-info в части синхронного создания клиента (т.к. мастер система по клиентам client-info и отказ в созданнии клиента со стороны данного сервиса должен приводить к отказу клиенту). На будущее: вынести логику работы с клиентами из core-app
2. Ускоряем работу core-app - добавляем кэш типа Redis, куда складываются события из Event-bus
3. Обеспечить контроль доступа к core-app от клиентов и партнеров
   1. Реализуем API GateWay (типа nginx)
   2. Балансировку нагрущзки на core-app на nginx или на k8s
   3. HPA (horizontal pod autoscaling) для core-app на k8s
   4. на API Gateway реализуем circut braker ограничение по RPS в ед. времени - стратегию нужно продумать
   5. client-info также выносим в API Gateway с целью уменьшить ожидания core-app от client-info что понизит нагрузку на червис
   6. В идеале применить HPA для client-info

### Решите, будете ли вы использовать паттерн Transactional Outbox.  
Не очень понять где здесь есть неолбходимость.
Но, если нет возможности доработки сервисов для перехода на Event-bus, то тогда можно применить подход Transactional Outbox, который позволит уменьшить доработку логики сервисов и их взаимодействий.
